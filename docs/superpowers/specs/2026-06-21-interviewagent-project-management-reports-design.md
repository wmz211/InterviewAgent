# InterviewAgent 软件项目管理报告体系设计

## 1. 目标与交付范围

为 InterviewAgent 建立一套面向真实软件项目管理场景的正式项目档案。代码仅用于识别产品范围和技术特征，报告主体依据项目治理、范围、进度、成本、质量、风险、资源和团队管理方法编制。

最终交付九份相互独立的中文 DOCX：

1. 项目建议书
2. 可行性分析报告
3. 项目计划书
4. 项目估算报告
5. 项目进度和成本控制报告
6. 项目质量管理报告
7. 项目风险管理报告
8. 项目团队建设和管理报告
9. 项目总结报告

项目计划书必须完整包含 WBS、资源计划、进度计划、成本计划、风险计划和质量计划；专题报告则提供执行过程、记录、指标、偏差与改进措施，避免简单重复计划内容。

## 2. 项目管理情境

- 项目名称：InterviewAgent 智能面试评估系统
- 团队规模：三人全职
- 王明哲：项目经理，兼核心 Agent 与 GraphRAG 负责人
- 江悦铭：后端负责人
- 周士斌：前端负责人
- 计划工期：20 周
- 模拟实际工期：21 周，反映语音集成和端到端稳定性整改造成的一周偏差
- 开发生命周期：阶段门控制下的迭代开发，每两周一个迭代
- 产品目标：交付支持简历与 JD 输入、多阶段智能面试、GraphRAG 技术追问、文本与语音交互、用户和会话管理、结构化评价报告的可验收系统
- 管理口径：以商业项目影子价格估算人力，不采用学生作业零成本口径

## 3. 统一基线设计

所有报告共享一个主数据集，包括项目章程摘要、范围边界、WBS 编码、里程碑、角色、计划工时、费率、成本科目、质量目标、风险编号和变更编号。

计划基线采用三人共 2,400 工时作为上限框架，根据阶段投入曲线分配，不机械假设三人每周投入完全相同。预算由直接人力、模型与云资源、软硬件及测试资源、管理储备构成。最终实际值设置为轻微超支和一周延期，并通过进度绩效指数、成本绩效指数、缺陷趋势、风险暴露变化和变更记录解释偏差。

具体金额和阶段工时在项目估算报告中自下而上计算后锁定，并同步回填其余报告。任何摘要金额均引用同一计算结果，不单独手工编造。

## 4. 九份报告的职责边界

### 4.1 项目建议书

说明业务问题、目标用户、拟建方案、预期收益、范围边界、主要干系人、初步周期与投资建议，形成是否立项的管理决策依据。

### 4.2 可行性分析报告

从技术、经济、运营、进度、法律合规和组织资源六个维度论证可行性，包含备选方案比较、敏感性分析和附条件立项结论。

### 4.3 项目计划书

作为执行基准文件，包含范围说明、WBS 与 WBS 字典、组织与 RACI、20 周进度基线、资源负荷、成本基线、质量计划、风险计划、沟通计划、配置与变更控制、验收和收尾安排。

### 4.4 项目估算报告

记录估算假设、类比估算、参数估算、三点估算和自下而上估算过程，给出资源、工期和成本结果及估算置信区间。

### 4.5 进度和成本控制报告

以阶段性状态日为观察点，使用挣值管理分析 PV、EV、AC、SV、CV、SPI、CPI、EAC 和 ETC，说明关键路径变化、偏差原因、纠偏措施和预测完工结果。

### 4.6 质量管理报告

区分质量规划、质量保证和质量控制，给出评审、测试、缺陷分级、质量门禁、度量结果、根因分析和持续改进记录。AI 特有质量包括回答相关性、阶段流转正确率、报告结构稳定性和 RAG 检索指标。

### 4.7 风险管理报告

建立概率影响矩阵、风险登记册和风险燃尽记录，覆盖 LLM 不确定性、模型接口、数据隐私、GraphRAG 质量、语音延迟、人员单点依赖、范围蔓延和部署安全等风险。

### 4.8 团队建设和管理报告

描述三人团队的组织设计、职责、授权、技能矩阵、工作协议、沟通机制、绩效目标、冲突管理、知识共享、人员负荷和团队发展过程，重点处理王明哲兼任项目经理与核心技术负责人的负荷风险。

### 4.9 项目总结报告

比较立项目标、计划基线和最终结果，说明范围交付、工期与成本偏差、质量与风险结果、验收情况、未决事项、经验教训和后续演进建议。

## 5. 文档结构与视觉规范

- 采用 `standard_business_brief` 设计预设，Letter 纵向、1 英寸页边距、Calibri 11 磅正文、蓝色三级标题。
- 使用 `editorial_cover` 的简化封面逻辑：独立封面、项目名称、报告名称、团队、版本和日期；正文设置安静的页眉页脚。
- 每份报告包含文档控制信息、摘要、正文、结论或审批建议，长报告增加目录。
- 仅对真实行列数据使用表格；说明性内容使用段落、编号步骤和项目符号。
- WBS、进度、预算、RACI、EVM、风险登记册和质量指标使用固定列宽表格，允许跨页重复表头，不设置可能截断文字的固定行高。
- 九份文件使用一致的编号、颜色、术语和版本标识，输出到独立交付目录。

## 6. 内容真实性规则

- 不把当前仓库状态直接冒充完整项目历史；管理过程数据明确作为基于目标系统范围构建的项目管理基线与案例记录。
- 不使用“零预算”“成员业余完成”等课程作业口径。
- 不把所有风险标记为已消除，也不把所有指标写成满分。
- 最终结果保留一周延期、轻微成本偏差、若干转入运维阶段的残余风险和技术债。
- 计划、控制和总结之间的所有关键数值必须可追溯且数学一致。

## 7. 生成与验证

使用捆绑 Python 运行时和 python-docx 生成文件。生成后执行结构审计，检查标题样式、表格几何、页眉页脚、编号、占位符和跨报告关键数据一致性。随后使用文档技能提供的 render_docx.py 将每份 DOCX 渲染为逐页 PNG，检查中文字体、表格换行、分页、裁切、重叠和空白页；发现问题后修订并重新渲染。

## 8. 验收标准

- 九份 DOCX 均可独立阅读和提交。
- 项目计划书包含用户要求的全部六类子计划。
- 三名成员姓名与职责在所有文件中一致。
- 计划工期统一为 20 周，最终实际工期统一为 21 周。
- 成本、工时、EVM 和偏差数据计算正确且相互吻合。
- 每份文档通过渲染检查，无明显乱码、文字裁切、表格溢出、重叠或异常空白页。
- 内容体现真实软件项目管理决策、控制和复盘，而非代码说明书或课程模板堆砌。
